# R-0431 — Under B1 tenant isolation is a correctness property, and the shared permission check had no mountain dimension

> **decision · done · adopted** · 2026-07-18 · §9
> Lifted from `docs/planning/completed/multi-tenant-architecture-decision-20260718.md` §5 (option B1)
> (`docs/planning/completed/multi-tenant-architecture-decision-20260718.md#5-B1@b77e5af`).

---

**Choosing one Firestore with `mountainId` scoping (B1) over a project per mountain (B2) trades
structural isolation for enforced isolation.** With separate projects, one mountain physically
cannot read another's data. With one database, **a missing `where` clause leaks one mountain's
content into another** — the same class of bug that Admin-SDK routes already have to
self-enforce, because they bypass the rules entirely.

⚠️ **Enforcement is heterogeneous — two mechanisms, not one.** Writes split across client-SDK
paths gated by `firestore.rules` **and** ~7 Admin-SDK API routes that bypass those rules. Under
B1 the `mountainId` check has to exist in **both**: in the rules for every client path, and in
the route code for every Admin-SDK path.

## The finding that changed B1's scope

🔴 **`hasPermission()` had no mountain dimension.** The permission-resolution function shared by
`firestore.rules` and `requireApiPermission` resolved role → permission with no `mountainId`
check at all. The concrete leak the framework named:

> `contacts` — the PII from 동참 submissions — was readable by _any_ `manage-users` holder. So
> granting mountain #2's owner `manage-users` for **their** mountain would have exposed
> **geyang's** contact PII.

🔑 **That is why B1 was not "add a tenant match per collection".** It required reworking the
shared permission-resolution logic itself — in the rules and in the API guard — plus a one-shot
backfill over existing production data. Scoping it as a per-collection sweep would have shipped
the leak.

## It was adopted and carried out

✅ **Verified against `config/firebase/firestore.rules` on 2026-08-09.** The shared function is
now `hasPermissionFor(userId, permission, mountainId)`, and it requires the mountain to be present
and active in the user's role map. The `contacts` clause reads:

```
allow read: if request.auth != null &&
  hasPermissionFor(request.auth.uid, 'manage-users', resource.data.mountainId);
```

The role model that made this expressible is `R-0401` (roles keyed by `mountainId`); the
regression net is `R-0094` (two-tenant isolation e2e), which references the `contacts` rules test
rather than duplicating it.
