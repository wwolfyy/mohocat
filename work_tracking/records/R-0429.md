# R-0429 — The `HANDOFF.md` import wrote all 57 record files with an empty body, and every count still reported success

> **bug · done** · 2026-08-09

---

**Symptom.** `work_tracking/records/R-0347.md` … `R-0403.md` — every record the `HANDOFF.md`
import produced, including all 36 migrated decisions — contained a correct H1, a correct
provenance line, a `---` rule, and **nothing else**. 37,489 characters of prose were missing.

**How it was found.** Not by a gate. While starting `R-0420`, the de-duplication rule (`R-0416`)
required probing new decision candidates against the reasoning already in the store, so `R-0395`
and `R-0400` were opened to read — and they were empty. The files are ~250 bytes each, which is
why nothing looked wrong in a listing.

## Root cause

```js
return { start, end, body: trimBody(lines.slice(start, end)) };   // locate() → the SPAN
...
    entry.body,                                                   // renderRecordFile() → the ENTRY
```

`locate()` returns the extracted prose on the **span**. `renderRecordFile()` read it off the
**entry**, where it has never existed.

🔑 **The reason this was silent is the whole lesson.** `renderRecordFile` builds the file with
`[...].join('\n')`, and **`Array.join()` renders `undefined` as an empty string** — not as the
text "undefined", which anyone would have spotted. So the template collapsed by exactly one line
and produced a well-formed markdown file with no body.

⚠️ **Every check the migration had was blind to it, and each for a defensible reason:**

- **`--expect <n>` counts rows, not bytes.** 57 records were extracted, 57 were written, 57 were
  checked in.
- **The fidelity verification ran against the extracted spans** — "all 57 bodies are verbatim
  substrings of the source" was true of `span.body`, which was correct throughout. It was never
  re-read off disk.
- **`build.js --check` compares `registry.md` to `registry.ndjson`.** The rows were perfect; only
  the files they pointed at were empty, and no gate looked at those.
- **`lib.test.js` and `workflow.test.js` test the tooling against a throwaway store**, so they
  never see the committed prose at all.

📌 **This is the failure mode the whole migration was built to prevent** — a tool that finds
nothing and reports success, the same shape as the jq measurement in restructure §4.3 and the
reason `R-0415` moved unknown-field rejection up into `lib.js`. It happened anyway, in the
migration's own importer, and it survived a session that declared the final gate met: _"a cold
session can answer 'has renaming the Firestore database been considered?' from the store alone —
`R-0368`, with the full reasoning in `records/R-0368.md`."_ `R-0368.md` was 254 bytes and held no
reasoning at all. **The gate was declared met by reading the row, not the record.**

## The fix

1. **`handoff.js` now renders `span.body`**, with a comment naming this record.
2. **`handoff-rerender.js`** re-rendered the 57 files from the archived body at the pinned commit.
   It does **not** re-import: it matches each stored record to its source entry **by title**,
   requires that match to be unique, and additionally checks that the record's `source_ref` names
   the matched entry's key. An ambiguous or missing match is a hard error, because pairing the
   wrong prose to a record is the one mistake that would be invisible afterwards. The store,
   `registry.ndjson` and `registry.md` were never touched — only the files were wrong.
3. **`tests/store.test.js`** is new, and it is the part that matters: the first test file that
   checks the **real, committed** store rather than a throwaway one. Every `detail_ref` resolves,
   no record file is header-only, every file's H1 names its own record, and no file in `records/`
   is orphaned.

✅ **The new assertions were mutation-tested rather than trusted.** Blanking one body fails "no
record file is header-only"; pointing one file's H1 at another record fails "every record file
names its own record". A suite that passes on its first run proves nothing — the same lesson this
repo recorded when four holes had to be punched in the Firestore rules on purpose.

## Recovered content

All 57, byte-identical to what the importer should have written the first time: 37,489 characters
from `docs/handoff/archive/2026-08-09-handoff-living-doc.md`, with the line spans in each file's
provenance line matching the ones the original import logged.
