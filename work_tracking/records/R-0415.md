# R-0415 — Unknown field names are rejected in `lib.js` rather than left to SQLite

> **decision · done · adopted** · 2026-08-09
> Migrated from `work_tracking/MIGRATION_JOB.md` — "Decisions made during execution" and the
> Phase 1 session entry (`work_tracking/MIGRATION_JOB.md#D-unknown-fields-rejected-in-js@44e08fe`).

---

**The insert names its columns.** A record carrying a typo'd field — `titel`, `soure_ref` — would
therefore be inserted successfully with that field simply not present, and nothing would say so.
The row would validate, the build would pass, and the content would be gone.

**That is the same silent-zero-rows failure restructure §4.3 measured jq for**, and it is the
failure mode this whole migration exists to remove: a tool that finds nothing and reports
success. So the check moved up into `lib.js`, where an unrecognised field name is a hard error
before SQLite is involved at all.

📌 It is part of a wider stance in the tooling: **`lib.test.js` rejects 15 malformed record
shapes** — the seven the design named, plus eight found while writing the tests — and every
importer in the migration throws on an input it does not recognise rather than skipping it.
`--expect <n>` on the extractors is the same idea at a different scale.
