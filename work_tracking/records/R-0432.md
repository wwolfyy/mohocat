# R-0432 — GA4 stays one shared property with a `mountain_id` dimension; per-mountain dual-tagging is deferred

> **decision · done · adopted** · 2026-07-19 · §9

---

**Q6, answered by the owner 2026-07-19: one shared GA4 property, segmented by a `mountain_id`
custom dimension. Dual-tagging deferred.** `R-0400` records the answer; this row carries the
constraint that makes it a real decision rather than a default.

⚠️ **GA4 permissions are property-level. There is no row-level restriction** — sub-properties and
roll-ups are Analytics 360 only, roughly $50k/year. So if mountain #2's owner is granted access to
the shared property, **they see geyang's numbers too.** The decision is fine while the second
mountain's owner is a delegate; it is not fine the moment they are an independent party who
expects their own reporting.

🔑 **The escape hatch is cheap and already possible.** `gtag.js` supports multiple measurement IDs
natively, so **dual-tagging** — send each event to a per-mountain property _and_ to a shared
roll-up — costs **$0** and needs no new infrastructure. It was deferred rather than rejected,
because nothing needs it until a second owner actually wants their own view.

📌 **What made the escape hatch possible was a different decision.** Analytics was moved off
`firebase/analytics` onto `gtag.js` precisely so measurement stops being welded to the one
Firebase app — see `R-0091`. Had analytics stayed on the Firebase SDK, centralizing auth would
have silently centralized analytics into a single property with no mountain dimension at all.

⚠️ **A timing constraint that is now satisfied, and would have been unrecoverable if missed:**
**GA4 does not backfill custom dimensions.** `mountain_id` had to be registered before mountain
#2's traffic began, or that traffic would have been permanently unsegmentable. It shipped as a
default parameter on 2026-07-26 (`R-0088`), before any second tenant exists.
