# R-0410 — The schema is not frozen — change it when changing it is the best fix

> **decision · done · adopted** · 2026-08-09
> Migrated from `work_tracking/MIGRATION_JOB.md` — "Decisions made during execution"
> (`work_tracking/MIGRATION_JOB.md#D-schema-not-frozen@44e08fe`).

---

**Owner's call, 2026-08-09.** The schema was designed from what was known at the time. Cases
nobody thought of will turn up, and when a schema change is the best fix, it gets made.

⚠️ **The two directions are not symmetric,** and the reason is structural: the build loads
`registry.ndjson` into a fresh database and re-validates the entire store on every run. A
tightened rule therefore invalidates every row written under the old one, retroactively.

| Safe — old rows still load        | Breaks history — old rows rejected  |
| --------------------------------- | ----------------------------------- |
| Add a nullable column             | Add `NOT NULL` with no default      |
| Add a column with a `DEFAULT`     | Remove an enum value                |
| Add an enum value                 | Tighten an existing `CHECK`         |
| Add a `CHECK` on a **new** column | Add a `CHECK` to an existing column |

🔑 **That table is a heuristic, not the rule.** The rule is that a change breaks history **iff
some row already in the store violates it** — and there is one systematic exception, found while
adding `deferred` (`R-0411`): **a `CHECK` conditioned on a new enum value cannot invalidate
history**, because no historical row can hold a value that did not exist when it was written.
`status <> 'deferred' OR note IS NOT NULL` is vacuously true for every earlier row, which was
verified against all 326 of them before the constraint went in.

That exception matters practically: without it, the table would have pushed the rule into
`checkin.js` — the one place a hand-edited `registry.ndjson` bypasses — instead of into
`schema.sql`, where every script enforces it.

- **Additive changes are free.** Edit `schema.sql`, rebuild, add a CHANGELOG line. No migration,
  no decision record, no ceremony.
- **Restrictive changes are a migration, not an edit**, and get a `decision` record either way.

📌 The first change under this policy was `type` gaining `question` (`R-0413`); the second was
`status` gaining `deferred` (`R-0411`). Both additive, both free.
