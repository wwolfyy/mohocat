# R-0414 — `checkin` stamps `work.json` with `checked_in` and never deletes it

> **decision · done · adopted** · 2026-08-09
> Migrated from `work_tracking/MIGRATION_JOB.md` — "Decisions made during execution" and the
> Phase 1 session entry (`work_tracking/MIGRATION_JOB.md#D-checkin-stamps-work-json@44e08fe`).

---

**`checkin.js` originally deleted `work.json` on success, which silently destroyed the
merge-conflict recovery procedure.** This was found by writing the tests, not by reasoning.

**The procedure it destroyed** (restructure §4.3): when two branches both revise the same record,
both append the same `rev` and git reports a conflict in `registry.ndjson` — which is the wanted
behaviour, and the reason there is no `merge=union` driver. Recovery is to take the incoming
`registry.ndjson` wholesale and re-run `checkin`, so `rev` is recomputed against the file you just
accepted. **That only works while `work.json` still holds your intent.** Deleting it on success
meant the file was already gone by the time the conflict appeared.

**What it does instead:** adds a `checked_in` date to the file. `checkout` reads that stamp to
tell a finished checkout (safe to replace) from an unfinished one (replacing it would lose edits
recorded nowhere else), which keeps `--force` a rare and deliberate act rather than a habit.

🔑 **The recovery path is now a test rather than a paragraph** — `workflow.test.js` drives it end
to end, so the next change that would break it fails instead of being discovered during a
conflict.
