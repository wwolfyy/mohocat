# R-0444 — R1 read as if new items were outside the loop, and the same-change rule was never numbered

> **change · done** · 2026-08-10
> Owner-raised: R1's `checkout → edit → checkin` phrasing could be read as requiring an existing
> item, which was never the intent.

---

**The reading is fair and the wording caused it.** R1 said _"every change to the store is
`checkout → edit work.json → checkin → build`"_, and "check out" implies there is something to
check out. There is not, for a genuinely new item: `checkout.js --new` opens a `work.json` with an
empty `records` array and the next free id, and you append to it.

✅ **Fixed as a clause on R1, not as a new rule** — and the reason is `R-0443`'s own test. Not
knowing `--new` does **not** fail silently: it either blocks you outright or pushes you toward
hand-editing a row, which R1 already forbids. It is **mechanism**, so the expansion went to
`WORKFLOW.md` §1 and R1 gained one line saying a new item uses the same loop and that having
nothing checked out is normal. 🔑 **Adding an R-number for it would have broken the criterion that
keeps the list short** — the list earns its place by being only the silent failures.

## The gap that was actually there

⚠️ **The same-change rule was in `AGENTS.md` §A but was not numbered**, sitting as a loose
paragraph forty lines below the list — while **R2 referred to it as "the same-change rule below"**.
So the numbered set was incomplete, and it was incomplete in the worst possible place: a rule that
fails silently in the strongest sense. Nothing stops you skipping a record, no gate fails, and the
work is simply invisible afterwards.

✅ **It is now `R4`**, and its evidence moved to `WORKFLOW.md` §2.3 under _"Explains R4"_, per the
`R-0441` layering. The paragraph it replaced is gone rather than duplicated.

🔑 **R4 says explicitly that unplanned work still gets a record.** The owner's framing was that in
an ideal world with good planning this should not arise. **It arises constantly, and legitimately.**
Every record written on 2026-08-10 — `R-0439` through `R-0443`, and this one — came from the owner
noticing something mid-session; not one existed as an open item beforehand. ⚠️ **A rule that framed
unplanned work as a deviation would make it a thing to avoid mentioning**, and the failure mode
would shift from unplanned to unrecorded, which is far worse. So R4 makes it ordinary and requires
the record either way.

## One more self-duplication

📌 **`AGENTS.md` was restating the `--out` guidance** in the `work.json` paragraph, a second copy
of what R3 now says. Removed with the same-change paragraph. **That is the second instance of
`AGENTS.md` duplicating itself** — `R-0442`'s audit compared the two files against each other and
never compared a file with itself, and this is the second thing that slipped through that gap.
🔑 **Worth remembering as a review habit rather than a rule:** when a document is long enough that
a statement can appear twice without the author noticing, checking it against itself is a distinct
pass from checking it against its neighbours.

## `rev 2` (2026-08-10) — R4 was written as if only the owner finds things

⚠️ **The first wording ended _"it is the ordinary case for anything the owner raises
mid-session"_,** which scopes R4 to owner-originated work. The owner asked whether an agent can
find something new mid-session. It can, constantly — and **that is the case where the record
matters more**, because an owner's remark at least exists in the conversation while an agent's
unrecorded finding leaves no trace anywhere.

📌 **The store's own history is the argument.** `R-0429` (57 record files imported with empty
bodies) and `R-0435` (ten records truncated mid-sentence) were both found by reading something for
an unrelated reason, and both had passed **every** gate. `R-0437` started as a link baseline taken
to prove a file move was safe, and the baseline turned out to be the finding.

✅ **R4 is now source-agnostic** — _"it does not matter who noticed"_ — and gained the clause that
was the real omission: **a finding you are not going to act on gets a record too, with
`status: open`.**

🔴 **Applied to this session immediately, because it was already being broken.** Two findings —
six record files whose frontmatter contradicts their row, and `README.md`'s stale hand-off label —
had been written into `R-0439`'s prose and reported in conversation, and neither was queryable.
They are now `R-0445` and `R-0446`. ⚠️ **That is the failure mode worth naming: writing a finding
into the prose of whatever you are doing feels like recording it.** It is not — nobody greps
records for other people's asides.
