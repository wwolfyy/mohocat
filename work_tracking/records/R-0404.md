# R-0404 — `build.js` also writes a gitignored `registry.db`, reversing "no .db is ever written"

> **decision · done · adopted** · 2026-08-09
> Amends [`work-tracking-restructure-20260808.md`](../work-tracking-restructure-20260808.md) §4.

---

**The original decision (2026-08-08, restructure §4) read: _"SQLite is used, but only as an
in-memory index built fresh on every script run. No `.db` file is ever written to disk or
committed."_** The owner reversed the first clause on 2026-08-09.

**Why it was reversed.** The store had no comfortable way to browse it. `registry.md` answers
"what is open?" but not an arbitrary question, `checkout.js --query` writes its answer to
`work.json` rather than showing it, and the NDJSON viewer extension tried in VS Code did not
work. The owner's words: _"I think I may have to take back what I said some time ago about not
producing a SQLite file from NDJSON. I want that database file so I can look it up easily in
VS Code."_

**What was actually at stake, and why this costs nothing.** §4.3 settled on NDJSON after ten
tests, on three grounds: line-level diffs, a reviewable pull request, and a **real git conflict**
when two branches revise the same record — the collision detector the whole `(id, rev)` primary
key exists to trigger. 🔑 **All three are properties of what is _committed_, not of what exists
on disk.** A binary committed beside the log would surrender all three at once; a **generated,
gitignored** file surrenders none of them. `registry.db` therefore has exactly the standing
`registry.md` already had — derived, rebuilt on every build, never edited by hand.

**How it is built.** `build.js` runs `VACUUM INTO` against the in-memory database it has already
loaded, so the file is a byte-for-byte dump of the same index every script uses — including the
`current_records`, `records_with_stale` and `children_progress` views, which are what make it
worth opening. ⚠️ `VACUUM INTO` **refuses to overwrite an existing file**, so the previous one is
removed first; the useful consequence is that a failed build leaves **no** file rather than a
stale one.

⚠️ **`--check` does not write it.** That flag is the CI gate, and a gate that writes a file is no
longer only checking. `work_tracking/tests/workflow.test.js` pins both halves.

🔑 **The narrower rule that replaces the old one: nothing may ever read `registry.db` as input,
and loading the store must never write a database.** The second half is a test
(`lib.test.js` — "opening the store writes no database file", which replaced the blanket
"no .db file is written to disk"). The first half is a convention, and it is the one to watch: if
a script ever opens `registry.db` to answer a question, the store has quietly acquired a second
source of truth, and the reversal will have cost what it was supposed to preserve.

📌 **Regenerating it is not a separate step** — every `build.js` run writes it, and `build.js` is
already step 4 of the normal workflow. Nothing new to remember.
