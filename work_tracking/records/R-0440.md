# R-0440 — Two guards written down: only checkin.js writes the store, and prose is finished before check-in

> **change · done** · 2026-08-10
> Owner-raised, after asking how the registry had been updated during the `R-0436` / `R-0437`
> session and finding the answer only partly written down.

---

**Neither rule was stated where anyone would meet it.**

- **"Only `checkin.js` writes `registry.ndjson`"** appeared twice, both times in passing and
  neither time as a rule: `SCHEMA.md` §8 mentions what "a hand-edited `registry.ndjson` would
  bypass" while arguing about where schema constraints belong, and the restructure doc says the
  same in a parenthesis. ⚠️ **`AGENTS.md` protected the wrong file** — it says `registry.md` is
  generated and must never be hand-edited, and said nothing at all about the store itself, which
  is the one where a hand-edit does real damage.
- **"Finish the prose, then check in"** did not exist anywhere.

**What prompted it.** The owner asked whether the registry was being updated as the work finished,
then whether `checkin.js` had been used at all. It had — four times, and no line of
`registry.ndjson` was ever hand-written. But the question was worth asking, because the honest
answer contained a real defect:

🔑 **`R-0437` was checked in as `done` while its work was still moving.** The record's prose
asserted _"`link.test.js` (17 assertions)"_. Four more assertions were then added — the
`WORK_TRACKING_LINK_ROOT` override that proves the gate exits 1 — and the figure was corrected **in
the prose file, with no new revision**. So `R-0437` reads `rev 2`, while the prose behind `rev 2`
changed afterwards and the store says nothing about it.

**Why that is a category of mistake and not a slip.** A record is **two artifacts** and only one of
them is versioned:

| Artifact             | Written by                | Versioned                        |
| -------------------- | ------------------------- | -------------------------------- |
| the row              | `checkin.js`, append-only | ✅ `(id, rev)`                    |
| `records/R-XXXX.md`  | any editor                | ❌ only the git diff shows it moved |

📌 **The owner's judgement was that this is acceptable in itself** — detail may change without the
revision number or the title changing, and versioning every wording tweak would make `rev` useless.
The guard is about **sequence**, not about forbidding prose edits: do the work, write the prose,
_then_ check in once, so the row and the file agree at the moment the row is written.

**Where they now live.**

- **`AGENTS.md` §A**, which every session loads, carries both in full — the rule and the reasoning,
  next to the check-out → check-in → build commands. Including the escape hatch: **a substantive
  correction after check-in is a new revision with a `note`, not a silent file edit.** Typos are
  not worth a revision; a changed claim is.
- **`WORKFLOW.md` §2**, which is read before a first check-in, carries the mechanism behind them —
  what a hand-written line skips (dry-run validation, the `(id, rev)` collision check, computed
  `rev`, merge shape), and `R-0437` as the worked example of checking in too early.
