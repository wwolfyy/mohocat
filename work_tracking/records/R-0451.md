# R-0451 — Replace next lint with ESLint directly, and resolve the two competing ESLint configs

> **task · open** · 2026-08-13
> Found on 2026-08-13 while answering what `next lint` does, during the `R-0450` discussion.

---

## Two reasons, and the second is the one with a live risk

**`next lint` is on its way out.** It is deprecated as of Next.js 15 and removed in Next.js 16, and
the migration path is to invoke ESLint directly. This repo is on `next@^14.2.29`, so nothing is
broken now, but the next major upgrade forces the change. Doing it ahead of the upgrade separates a
lint change from a framework change, which is worth something when one of them goes wrong.

**There are two ESLint configs and they disagree.** Both exist at the repository root:

| File                | Format | Extends                                | Rule overrides                          |
| ------------------- | ------ | -------------------------------------- | --------------------------------------- |
| `.eslintrc.json`    | legacy | `next/core-web-vitals`                 | `react/no-unescaped-entities` **off**   |
| `eslint.config.mjs` | flat   | `next/core-web-vitals`, `next/typescript` | none                                 |

On `eslint@^8.57.1` the legacy file wins unless `ESLINT_USE_FLAT_CONFIG` is set, so
`eslint.config.mjs` is almost certainly dormant today. ⚠️ **The risk is that the two differ in what
they check.** The flat config adds `next/typescript` and does not disable
`react/no-unescaped-entities`, so anything that flips the project to flat config — an ESLint 9
upgrade, a tool that defaults differently — silently changes the rule set and can surface
violations that look like they appeared from nowhere.

## The work

Replace the `next lint` invocation in `.lintstagedrc.js` with a direct `eslint` call, and the
`lint` script in `package.json` with the same. Then pick **one** config and delete the other,
recording which and why.

📌 **Deciding which to keep is the real content of this task, not the script change.** Keeping the
flat config is the forward-looking choice, since ESLint 9 makes it the default and `next lint` is
going away regardless. But it currently checks *more* than the legacy file does, so adopting it
will produce violations that the repo has never had to answer, including whatever `next/typescript`
adds and every `react/no-unescaped-entities` hit that the legacy config has been suppressing.

⚠️ **Do not do this in the same change as `R-0452`.** That record is about whether warnings should
fail the build. Changing which rules run and whether warnings are fatal at the same time makes it
impossible to tell which change produced a given failure.

## Watch-out

`next lint` restricts itself to the directories Next.js cares about — `app/`, `pages/`,
`components/`, `lib/`, `src/`. A direct `eslint` call has no such default and will lint whatever it
is pointed at, so the invocation needs an explicit path list or an `ignores` block. Otherwise the
first run will report on `work_tracking/scripts/`, `scripts/`, and the test directories, which have
never been linted and were not written to be.
