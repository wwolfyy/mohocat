**The tracker's own header has said since 2026-08-08 that it should end up in the registry:**
_"if the registry cannot track its own migration, it will not track anything else."_ Its
**Decisions made during execution** table said the same in plainer words — _"Migrate these into
the registry as `type: decision` once it is live"_ — with **14** of them sitting in a markdown
table. The registry went live on 2026-08-09.

🔑 **Why it goes first rather than last** (owner, 2026-08-09, correcting an earlier
mis-sequencing). The value of a dogfooding test is in _finding out_, and a test run at the end
discovers nothing: everything is already built on the assumption it works, with no budget left to
change course if it does not. This repo has recorded that lesson twice — the rules suite that
**passed on its first run and proved nothing** until four holes were punched in the rules on
purpose, and the **P0 characterization net written before the refactor**, because a net written
afterwards pins whatever you happened to build.

📌 **It was already costing something measurable.** The "403 records" rot fixed on 2026-08-09
happened _inside this file_, because it hand-maintained a status table, a phase table and a
source-file table that are all projections of state the registry already holds — the exact
failure this workstream exists to remove, living in the workstream's own tracker.

🔑 **What this actually tests is not "can the registry hold things".** Every record imported
before it was historical or settled. **Nothing had yet been carried as live, iterative work** —
checked out, revised across sessions, re-checked-in. That is the case that matters from Phase 5
on, and it was the one still unproven.

## What the test found

✅ **Done 2026-08-09.** 24 records written — 14 `decision`, 10 `task` — and `MIGRATION_JOB.md`
stubbed in the same commit, **618 → 437 lines**, with `HANDOFF.md` and the migration plan
repointed at the records. 📌 The cut is modest because **the 332-line session log stays**: it is
narrative, and narrative is not state. What went was the live state — the status table, the phase
table, the source-file table, the resume list, the decisions table and the definition of done.

🔑 **The live-work path works, and this record is the proof.** It was checked in at
`in-progress`, the stub was written, then it was checked out again and revised to `done` — so it
is the **first record in the store at `rev: 2` from real work** rather than from a re-import, and
`rev: 1` is still in the log saying it was in progress. Nothing about the workflow needed
changing to carry it.

🔴 **It found one thing, which is what a test is for: `R-0428`.** The owner settled on 2026-08-08
that `PROJECT_PLAN.md` and `HANDOFF.md` move into `work_tracking/`. The move never happened and
**no phase of the plan schedules it**. It survived unnoticed because it was written down twice —
once as a row in a decisions table, once as an answered question — and neither of those shapes is
a piece of work anybody reads back. In the registry it is an open task, and
`--query "status = 'open'"` returns it.
