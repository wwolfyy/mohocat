## 1. The task: 동참 contact form, Variant A

**Goal:** a submission to `/pages/contact` should (1) be recorded in Firestore and
(2) email the admin — without any Firebase compute, on Vercel.

**The agreed design (handoff-5 §2):**

> Form → `POST /api/contact` → route verifies the Firebase ID token → writes the contact
> via the **Admin SDK** → sends the email (nodemailer/SMTP) to `adminEmail` → admin sees
> it in the Contact Management tab.

Variant A was chosen over a Firestore-trigger Cloud Function because the trigger is a
backend DB event only Cloud Functions/Eventarc can subscribe to — it **can't run on
Vercel**. An HTTP route can. See [[contact-form-notification-design]].

## 3. What to build (the remaining work)

1. **`POST /api/contact`** — `src/app/api/contact/route.ts` (absent today):
   - Read the body (name/contact/message — match the form's `formData` shape in
     `pages/contact/page.tsx`).
   - **Write the contact via the Admin SDK** (`@/lib/firebase-admin`), server-side, so
     the write bypasses client rules.
   - **Send the email** via nodemailer/SMTP to `adminEmail`
     (`getMountainConfig().adminEmail` / read from `mountains.json`).
   - Return `{ success }` / structured error. Per CLAUDE.md: `try/except` that logs +
     re-raises (no silent swallow); never log PII (the submitter's contact info) or SMTP
     creds.
2. **Repoint the form** — `pages/contact/page.tsx` `handleSubmit`: replace the direct
   `contactService.createContact(...)` call with `fetch('POST /api/contact', …)`.
   (Adding `/api/contact` as a referenced route means the **smoke count goes 23 → 24** —
   expected; the smoke suite asserts referenced routes have a handler.)
3. **Revise the `contacts` rule** to server-only writes. Current shape allows direct
   client creates:
   ```
   match /contacts/{document} {
     allow create: if request.auth != null;     // ← change to: if false (Admin SDK bypasses rules)
     allow read:   if request.auth != null && hasPermission(request.auth.uid, 'manage-users');
     allow update, delete: if false;
   }
   ```
   With Variant A the app never writes as a client, so `create` becomes `if false`
   (deny all client writes; the Admin SDK route is the only writer). Then
   `firebase deploy --only firestore:rules`.

**Reusable email code:** the nodemailer/SMTP logic from the abandoned Cloud Function is
recoverable from history —
`git show f62816b~1:functions/src/index.ts` (the `functions/` dir was removed in the
Phase 1 cleanup commit `f62816b`). Relocate that SMTP logic into the route; keep the
transport provider-agnostic SMTP.

## 4. Watch-outs / decisions to surface

- **SMTP provider + secrets.** Pick a transactional SMTP (SendGrid/Mailgun/SES over
  Gmail, for deliverability). New env vars (host/port/user/pass/from) must be added to
  **Vercel** (Production + Preview) via Terraform (`infra/terraform/`, the `shared_envs`
  block) — confirm with the user before wiring. Never commit creds.
- **RBAC collection drift (blocks the read rule).** The `contacts` read rule calls
  `hasPermission(uid, 'manage-users')`, which reads `user_permissions/{uid}` — but the
  app writes roles to `users/{uid}` (PROJECT_PLAN §7 "RBAC collection drift"). Verify the
  admin actually resolves `manage-users` before trusting rule-level read enforcement.
- **ID-token verification.** Admin `/api/*` routes don't consistently verify a bearer
  token today (PROJECT_PLAN §7). For `/api/contact` the write is public-ish (anyone can
  submit a contact), so token verification may be optional for the **write** — but decide
  deliberately, and rate-limit/validate input to avoid spam.
- **No request validation library.** Validate the body shape in the route (no zod in the
  repo yet); reject missing/oversized fields.
