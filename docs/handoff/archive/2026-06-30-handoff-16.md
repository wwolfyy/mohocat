## 1. Firebase SDK inventory + analysis (committed `066a5c4`)

New doc [`docs/planning/firebase-sdk-usage-inventory.md`](../planning/firebase-sdk-usage-inventory.md):
where Client SDK vs Admin SDK are used, and an analysis of migrating the privileged
client-SDK writes to the Admin SDK. **Conclusion (also in PROJECT_PLAN §7):** the blanket
"Admin SDK for all writes" target is **retired**; instead —

- **Tier 1 — `users` + `permission_logs`: MIGRATE** (strong yes; not yet scheduled). Audit
  integrity is impossible client-side (role-change audit writes to `permission_logs` are
  currently denied + swallowed → every role change loses its audit entry); roles are the
  escalation-sensitive surface; low effort.
- **Tier 2 — `cats`/`cat_images`/`cat_videos`/`about_content`/`posts_announcements`: DEFER**
  (rules-gated client writes are adequate; migrate only when touching for validation).
- **Not a target:** community/user-as-owner writes (legitimate Client SDK); dead paths
  (`contact-service.addContact`, `point-service` writes) are cleanup.

Nothing was migrated — this is analysis only. Tier 1 is the warm next candidate if/when
the SDK workstream is picked up.

## 4. ⭐ NEW DIRECTION — one design principle + shared primitive set, public **and** admin

**Owner decision (2026-06-30).** The job has **two parts, both in scope together:**

1. **Design principle** — a reusable **primitive set** + a **consistent styling mechanism**
   applied across the **whole app (public + admin)**, covering the areas the principle does
   NOT yet cover in the public UI (e.g. no shared `Button`/`Card` today).
2. **Actual branding** — apply the **brand across the board, including admin.** The admin UI
   **IS brought under the public brand** — the prior "admin stays a deliberately utilitarian
   tool" stance is **retired** (owner wants to deal with branding while doing this). So this
   is _not_ just structural consistency; admin gets re-skinned to the brand too.

Context (today's state, verified): the public side already applies the reuse principle
**selectively** — strong for **modals** (`src/components/ui/` Modal/Lightbox/VideoPlayer),
**album/media** (`src/components/album/*`), shared **hooks**, centralized **strings**
(`src/constants/strings.ts`), and **design tokens** (`tailwind.config.js`). But it is **not
a complete atomic primitive set** — e.g. there is **no shared public `Button` or `Card`**;
those are hand-rolled with Tailwind + brand tokens (consistently, but not as components).

**What the next session should do (restart of the design + Korean tasks under this lens):**

1. **Define the unified primitive set + principle** — the missing atomic primitives
   (`Button`, `Card`, form `Input`/`Field`, `Alert`/banner, `Table`?, etc.) that BOTH
   public and admin consume, alongside the existing `Modal`/album primitives.
2. **One component set, token-driven** — a single shared primitive set consumed by both
   public and admin, styled from the brand tokens (`tailwind.config.js`). **Not** two
   parallel trees, and **not** a separate utilitarian admin theme — admin renders in the
   brand like everything else.
3. **Reconcile the admin Core primitives (§3) into this shared set AND re-brand them.** The
   `admin/ui` `Button`/`Card`/`Alert` are a **starting template**, but two things about them
   are **superseded:** (a) "admin-specific, separate from public" → move to / merge with the
   shared location; (b) their **utilitarian gray palette** → adopt the **brand tokens**.
   Don't entrench `admin/ui` as a permanent silo, and don't keep the gray look.
4. **Fold Korean translation into the same pass** — the deferred admin Korean-strings item
   restarts here; decide whether to add an **admin strings module mirroring
   `src/constants/strings.ts`** (or centralize all copy) as part of the system, not as a
   separate sweep over the same files.

**Settled (do NOT re-litigate):**

- **Admin IS branded** (see decision above) — re-skin admin to the public brand; the
  utilitarian-tool stance is retired.
- **The two §3 carve-outs** (admin active-tab yellow, login gradient) are **kept and folded
  into the brand** — they were the right direction, not exceptions to undo.

**Still open for the next session (don't assume):**

- **The exact styling mechanism** — how the shared primitives consume brand tokens (variant
  props, CVA-style recipes, plain Tailwind + token classes, etc.). Pick one and apply it
  uniformly.
- **Scope/sequencing** vs. admin-mobile (§6) and redesign Phase C (the public other-pages
  brand audit) — the unified branded system is the natural foundation for both; likely do
  the system first, then C and §6 on top of it.
