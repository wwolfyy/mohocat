## 1. Overlay stacking — dynamic z-index (`8c1c5ee`)

**Symptom:** from the map (feeding spot → cat gallery → cat → 사진/동영상 보기) the album
modal opened **behind** the cat-detail modal; it worked from the 입양홍보 page.

**Root cause:** hand-maintained z-index. `CatGallery` opened the cat-detail modal at
`z-[60]`; the album modals used `Modal`'s default `z-50` → behind. From adoption the cat
modal is `z-50` and the album (also `z-50`) mounts later → on top, masking it. A naive bump
couldn't work: `Lightbox`/`VideoPlayer` render **inside** the cat modal's stacking context
(not portaled), so raising the album would clear them too.

**Fix:** made overlay z-index **dynamic** off the existing `useModalLayer` stack (already
tracks open overlays for keyboard). `useModalLayer` now returns a z-index from stack depth
(`50 + depth·10`); `Modal` applies it (the `zIndexClassName` prop + its 2 call-site
overrides are gone); `Lightbox`/`VideoPlayer` now **portal to `<body>`** and use the same
z-index, so they escape confinement and always sit above the album at any depth.
**Files:** `useModalLayer.ts`, `Modal.tsx`, `Lightbox.tsx`, `VideoPlayer.tsx`,
`CatGallery.tsx`, `CatInfo.tsx`. Owner-verified on the map flow.

## 2. Login error UX — one banner + Korean Kakao copy (`fbcefaa`)

Two related auth-UI fixes in one commit:

- **Shared error banner.** `LoginForm` rendered email + Kakao errors in a block **inside the
  email `<form>`**, so Kakao failures looked like email errors. Moved both into **one shared
  banner at the top** of the form; removed the in-form block. Phone login keeps its own
  field-adjacent inline errors (owner's call — they're contextual validation, never
  misattributed).
- **Korean Kakao messages.** `auth-service.signInWithKakao()`'s `catch` mapped
  `error.code` → **hardcoded English** (and the `default` relayed raw upstream English).
  Added `strings.auth.kakao.errors` (Korean) and mapped to it, **keeping the verbose
  `console.error` diagnostics**; config/unknown codes + upstream detail collapse to a
  generic Korean message (console-only detail). Also Koreanized the provider-not-enabled and
  fallback-failure throws and `AuthProvider`'s English fallback.
  **Files:** `LoginForm.tsx`, `strings.ts`, `auth-service.ts`, `AuthProvider.tsx`.
  Note: `let errorMessage: string` is required — `strings` is `as const`.

**Verify caveat:** the **banner placement** was owner/agent-verified via an email-login
failure. The **Korean Kakao string** was **not** captured live — driving real Kakao OAuth

## 3. Map re-fit on window resize — desktop done, mobile pending (`a61f1d9`)

**Symptom:** resizing the window left the map at its old size → white margins (grow) /
clipping (shrink); the 전체 보기 fit control fixed it.

**Root cause:** the container is `h-full w-full` (resizes with the window), but Leaflet's
`trackResize` only keeps the canvas size synced (`invalidateSize`) while **preserving
zoom** — nothing re-fit the view.

**Fix:** in `MapViewController`, a debounced (150ms) window `resize` now calls
`map.invalidateSize({ animate: false })` then `map.fitBounds(bounds)` — the same
`applyFit()` the fit control runs (`invalidateSize` first so the fit measures the new size).
**File:** `LeafletMountainMap.tsx`.

**Status:** ✅ **desktop confirmed** by the owner in a real browser. ⏳ **mobile pending** —
owner saw irregularities at mobile widths. Tracked as a new item in **PROJECT_PLAN §4**
("Map re-fit on window resize — mobile"), which must cover the portrait layout and the
landscape↔portrait remount boundary (`key={isMobile}`).

**Tooling watch-out (important):** this map **cannot be resize-tested via automation** —
`resize_window` didn't change the page viewport, and simulating a resize by poking the
container height + dispatching a synthetic `resize` event produces **false negatives** (even
the known-good fit button fails under it, because `fitBounds` reads Leaflet's real
layout-driven size cache). **Verify map-resize behaviour in a real browser only.**
