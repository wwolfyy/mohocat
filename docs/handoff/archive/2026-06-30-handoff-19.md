## 1. The bug: `/pages/butler_stream` — missing Firestore rule

**Symptom:** the page rendered but `FeedingSpotsList` showed its error state; console:
`Error fetching feeding spots: FirebaseError: Missing or insufficient permissions`
(+ a `Failed to load permission config` line — see §2).

**Root cause:** `FeedingSpotsList` reads the **`feeding_spots`** collection via the **client
SDK** (`getFeedingSpotsService()` → `feeding-spots-service.ts`, `db` from `./firebase`).
`firestore.rules` had **no `match /feeding_spots` block at all**, so it fell through to the
default `allow read, write: if false`. The check-in **write** (`updateFeedingSpots`, via
`NewPostForm`) had the same exposure.

**Why it hid:** the writes inventory attributed butler*stream's feeding reads to the
**Admin-SDK** services (`feeding-spots-admin-service` / `basic-feeding-spots-service`, which
bypass rules) — but those only back `/api/feeding-spots-basic` + the build-time `new`-post
page. The on-page list uses the parallel **client** path, which \_is* subject to rules. So
nobody noticed the collection needed a client read rule.

**Fix** (`firestore.rules`, mirrors `posts_feeding`):

```
match /feeding_spots/{document} {
  allow read: if request.auth != null;
  allow write: if request.auth != null && hasPermission(request.auth.uid, 'manage-posts');
}
```

The page is admin/butler-gated and `posts_feeding`/`posts_butler` use the same pattern, so
authed-read + `manage-posts`-write is consistent. **Deployed by the owner** (live).

## 2. R3 decision: `role_permissions/role-config` client read

The `Failed to load permission config` line is a **separate, pre-existing** issue (not the
page break): `permission-service.loadConfig()` reads `role_permissions/role-config`
client-side, was **denied** (no rule), caught the error, and fell back to **bundled local
JSON** (`config/permissions.json`). Functionally survived, but the client UI then resolves
permissions from **stale** config that drifts from the live matrix.

**Key finding that settled it:** _both_ enforcement paths already read the **live** doc —
the `hasPermission()` rule (`get()`) and `requireApiPermission` (Admin SDK). Only the client
UI was out of sync. The matrix is **config, not PII/secrets**, and it must be readable by
**every authed user** (each resolves its _own_ role). The existing
`GET /api/admin/role-permissions` is `manage-users`-gated, so an API route can't serve
butler/viewer roles.

**Decision → R3-(a): add an authed read rule** (`role_permissions/role-config`,
`read: if request.auth != null`; `write: if false` — writes stay Admin-SDK-only). Now the
client resolves from the live matrix and the console error is gone. **Deployed (live).**
`role_permissions/resource-config` is left as the model **R3-(b)** (read/written only via
`/api/admin/resource-permissions`; no client path).

  rule-gated; PII-off-the-wire migration logged, not actioned).

## 7. Gotchas / notes

- **`feeding_spots` has two SDK paths** — client (`feeding-spots-service.ts`, subject to
  rules; powers the butler*stream \_page* + NewPostForm) and Admin (`*-admin-service` /
  `basic-*`, bypasses rules; powers the API route + build). Don't conflate them — that
  conflation is exactly what hid the missing rule.
- **`role_permissions` live vs bundled JSON** — enforcement (`hasPermission` rule +
  `requireApiPermission`) reads the **live** Firestore doc; before this fix the client UI
  read **bundled `config/permissions.json`**. They can drift; the R3-(a) rule realigns the
  client onto live config. The local JSON remains as the fallback if the read ever fails.
- **Rules deploy is manual + separate from `git push`** — editing `firestore.rules` does
  nothing to the live app until `firebase deploy --only firestore:rules`. (Owner did this.)
