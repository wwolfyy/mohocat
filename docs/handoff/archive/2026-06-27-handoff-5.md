## 1. Findings — the messy deployment target

The repo carries **four** historical deploy paths. The confusion that triggered this
reckoning: the app used to be **static on Firebase Hosting**, but that's retired —
yet Firebase config still litters the repo, which made a Firebase-Functions design
look natural when it isn't.

| Target                           | Evidence                                                                                                  | Reality                                                                                                                                |
| -------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Firebase Hosting (static)**    | `.github/workflows/firebase-hosting-{merge,pull-request}.yml`                                             | ❌ Retired — both fully commented out ("replaced by Cloud Run; Next.js image optimization requires a server runtime"). The static era. |
| **Google Cloud Run**             | `deploy-cloud-run.yml` (manual), `Dockerfile`, `cloud-run:deploy-backup` script, `next.config.js` comment | Historical compute target                                                                                                              |
| **Home server (Docker Compose)** | `deploy-home-server.yml` (auto on push to `main`, self-hosted runner)                                     | Historical compute target                                                                                                              |
| **Vercel**                       | `vercel-build` script (no `vercel.json`/`.vercel/`/workflow)                                              | ✅ **The chosen target** (per user) — wired via the Vercel dashboard.                                                                  |

### What MUST stay Firebase regardless of where compute runs

The crucial separation: **Firestore (DB) + Auth are Firebase; compute is Vercel.**
These are independent.

- **Firestore security rules** always deploy to Firebase (`firebase deploy --only
firestore:rules`) no matter where the app is hosted. → The **rule + the
  `firestore.rules` wiring in `firebase.json` are keepers.**
- The **admin read path** (Step 1) reads Firestore and is host-agnostic. → Keeper.

### What changes BECAUSE the target is Vercel

- **No Firebase Hosting / no Firebase Functions / no Cloud Run / no home server.**
- The **Cloud Function** can't be ported to Vercel anyway: an `onDocumentCreated`
  Firestore trigger is a backend DB event only Cloud Functions/Eventarc can
  subscribe to — Vercel routes are HTTP-invoked, not event-driven. → Abandon it.
- `firebase.json` should shrink to **just** `{ "firestore": { "rules": ... } }`
  (drop the `hosting.frameworksBackend` and `functions` blocks).

## 2. The notification design — Next.js API route (Variant A) > Firebase trigger

**Preferred (being adopted): Variant A — server-side write via the Admin SDK in a
Next.js API route.**

> Form → `POST /api/contact` → route writes the contact to Firestore (Admin SDK) →
> route sends the email (nodemailer/SMTP) → admin sees it in the Contact Management
> tab.

Why:

- **Runs on Vercel** (and anywhere the Next app runs) — no Firebase compute, no
  Blaze-for-functions, no separate `functions/` package.
- **Confirmed with the user:** the Firestore DB still records every contact and the
  admin page still manages them — the notification mechanism is orthogonal to
  storage + admin reads.
- Pairs naturally with the **server-enforced gate**: the route verifies the Firebase
  ID token, and because the Admin SDK bypasses rules, the `contacts` rule becomes
  **deny all client writes (server-only)** — stronger than "allow if `request.auth`".
  _(This revises the rule shipped this session, which currently allows
  `create: if request.auth != null` for direct client writes.)_

Trade-off accepted: a Firestore trigger would fire on _any_ write (incl. console);
the route only fires for app submissions — fine, since the form is the only writer.

The **nodemailer/SMTP logic already written is reusable** — it just relocates from
the Cloud Function into the API route. Transport stays provider-agnostic SMTP (no
vendor lock-in; recommend pointing it at a transactional provider's SMTP relay,
e.g. SendGrid/Mailgun/SES, over Gmail for deliverability). Recipient stays
`adminEmail` in `config/mountains/mountains.json`.

⚠️ Dependency to verify when implementing: the read rule uses
`hasPermission(... 'manage-users')`, which reads `user_permissions/{uid}` — see the
**RBAC collection drift** note in PROJECT_PLAN §7 (`firestore.rules` reads
`user_permissions` while some code writes `users`). Reconcile before relying on it.
