## 0. Where we are (read first)

**The admin Cat CMS can't save edits** — "Failed to update cat with id: …". Root cause: the
deployed Firestore rules lock the `cats` collection to `allow write: if false`, but the admin
CMS writes via the **client SDK**. **A rule fix is staged** (`cats` → permission-gated
`manage-cat`); **it is not yet deployed**. This is **not** a §7a regression.

This hand-off is so the fix can be **deployed + verified in a fresh session** (deploying rules
and signing into `/admin` are owner actions the assistant can't do).

## 1. The bug + root cause

- **Symptom:** editing any cat in `/admin` (고양이 관리) → red banner "Failed to save cat: Failed
  to update cat with id: …". Systematic across cats.
- **Why:** `config/firebase/firestore.rules` had `match /cats/{x} { allow write: if false }`.
  The CMS (`src/app/admin/cats/page.tsx` → `getCatService().updateCat`) writes with the **client
  SDK**, which Firestore rejects → permission-denied. `cat-service.ts` swallows the real error
  and rethrows the generic message (so the UI hides "Missing or insufficient permissions").
- **When it broke:** the `if false` rule had long been in the file but went **live** when the
  동참 contact feature ran `firebase deploy --only firestore:rules` (`f84f3c1`). **Not** caused by
  the §7a work (which doesn't touch `cats` writes or the rules). _Aside:_ the §5 on-demand
  `triggerCatRevalidate` wired into the CMS never runs today — `updateCat` throws first.

## 2. The fix (STAGED, not deployed)

`config/firebase/firestore.rules`, `cats` block now:

```
allow write: if request.auth != null && hasPermission(request.auth.uid, 'manage-cat');
```

`manage-cat` is the real permission key (`src/config/permission-config.ts`); `hasPermission`
reads `users/{uid}.currentRole.permissions` + `.isActive`. This mirrors the existing
`posts_feeding` / `posts_butler` rules — i.e. permission-gated **client** writes, which are a
genuine (server-enforced) security boundary, not a client-only check.

## 3. Resume — deploy + verify (do this first)

1. **Deploy the rules:** `firebase deploy --only firestore:rules`.
2. **Browser-verify in `/admin`** (needs an owner login): edit a cat (e.g. 깡패) → it saves, no
   banner. Confirm the **§5 on-demand revalidation** now fires (admin edit → public `/` reflects
   without a redeploy — this is also handoff-9's pending preview check).
3. _Secondary, latent:_ `db = getFirestore(app)` has **no `ignoreUndefinedProperties`**, so a
   save with unset `isNeutered`/`date_of_birth` can still throw `Unsupported field value:
undefined` even after the rule fix (깡패 has both set, so it'll save). If it bites: either
   `initializeFirestore(app, { ignoreUndefinedProperties: true })` or sanitize undefineds in
   `createCat`/`updateCat`. Flag, don't pre-fix.

## 5. Future consideration (NOT a scheduled task)

Migrate admin writes to **Admin SDK API routes** (verify ID token + permission → server write),
restoring `write: if false` and **eliminating client-SDK write reliance** — the "Admin SDK is the
only writer" direction the 동참 work started. Effort/risk **not yet assessed** (owner wants to
scope it before committing). Notes for when it's evaluated:

- It would give server-side validation + fully-locked collections; it would **not** shrink any
  client bundle (the Firebase SDK already ships app-wide via `AuthProvider` → `firebase/auth` in
  the root layout, and onto the home page via `MountainViewer → thumbnailPreloader → @/services`).
- Truly dropping the SDK from **public** bundles is a separate, bigger effort: no public client
  component importing `@/services`, **and** `AuthProvider` lazy-loading `firebase/auth`.
