## 1. What shipped this session (동참 Variant A + deployment docs)

**The feature (committed `f84f3c1`, pushed):**

- **`POST /api/contact`** — `src/app/api/contact/route.ts` (new). Verifies the Firebase
  **ID token** (`Authorization: Bearer …`), validates + length-caps the body, writes the
  contact via the **Admin SDK** (`@/lib/firebase-admin`, bypasses client rules), then emails
  `adminEmail` over **SMTP/nodemailer**. Node runtime pinned. An email failure logs + returns
  `{ success:true, emailDelivered:false }` so a notification miss never loses the recorded
  submission. No PII/creds logged.
- **Form repointed** — `src/app/pages/contact/page.tsx` `handleSubmit` now `fetch`es the route
  with the ID token (was a direct client `createContact`).
- **Rule tightened** — `config/firebase/firestore.rules`: `contacts` `create → if false`
  (Admin SDK is the only writer); deployed via `firebase deploy --only firestore:rules`.
- **SMTP** — Gmail (`SMTP_HOST/PORT/USER/PASSWORD/FROM`), set in local `.env` **and** the
  Vercel dashboard (Production + Preview). Uses a Gmail **App Password** (16 chars, spaces
  stripped). `nodemailer` + `@types/nodemailer` added.

**Deployment docs + IaC reframing (committed `dcf7715`/`0efe3cf`, pushed):**

- **Key finding:** Terraform is **not actually used** for deployment. The live process is
  plain **`git push`** → Vercel Git integration (`main`→Production, `dev`→Preview); env vars
  are **hand-managed in the Vercel dashboard**. No state was ever persisted; earlier `apply`s
  errored. See [`docs/deployment/README.md`](../deployment/README.md) (the new source of
  truth).
- The Terraform config was **parked**: renamed `infra/` → `_infra/`, `terraform/` →
  `_terraform/`, files `_main.tf`/`_variables.tf`/`_outputs.tf`/`_terraform.tfvars.example`
  (underscore = stale). `.gitignore` / `.prettierignore` / `AGENTS.md` updated to match.
- Two Terraform walkthroughs kept **for future consideration** (multi-tenant / DR), each with
  a "NOT THE CURRENT PROCESS" banner: `vercel-terraform-walkthrough.md` (adoption + import
  pass) and `vercel-terraform-greenfield.md` (from scratch). SMTP plumbing was added to the
  parked `_terraform` files as a blueprint only.

## 3. Next workstream: §7a — bake the data layer (perf 🔴)

Full detail in [`PROJECT_PLAN.md` §7a](../planning/PROJECT_PLAN.md) (L220–284). The essentials:

**Problem.** The app reads Firestore **live from the browser** on key surfaces, gating content
on a serial client-side waterfall (hydration → Firebase Web SDK init → cold Firestore → query)
and shipping the heavy `firebase/*` SDK to the client. Worst case ~0.6–1.5 s+ of late-arriving
content.

**Hotspots:**

- **Landing map cat avatars** — `src/components/LeafletMountainMap.tsx` (`usePointMarkers`,
  ~L63–99): N parallel `getCatsByPointId` queries in a post-hydration `useEffect`. Points are
  baked (fast), but cat faces pop in late.
- **Galleries** — `CatGallery` and `/pages/adoption` call `getAllCats()` client-side
  (spinner-gated).

**Baseline that already does it right (extend this):** `src/app/page.tsx` is an async Server
Component that `await`s `getPointService().getAllPoints()` with no `dynamic`/`revalidate` →
points baked at build. Thumbnail image files are likewise build-fetched
(`scripts/maintenance/fetch-static-assets.js`). The fix extends "bake occasional-change reads"
from points/images to cat **metadata**.

**Direction (design with the user before coding):**

- Move occasional-change reads (cats; the `{ pointId → chosen thumbnail }` map) to build/server
  via **Server Components + SSG/ISR** (`revalidate`) and/or **on-demand revalidation on admin
  save** (keep "admin edits reflect quickly" without manual redeploy).
- Bake the marker `{ pointId → thumbnail }` map in the home Server Component → **zero client
  Firestore queries** for avatars; consider dropping the Firestore SDK from those bundles.
- **Tech-debt:** `page.tsx` uses the client Web SDK on the server — evaluate the **Admin SDK**
  for server/build reads (already used by `fetch-static-assets.js`).
- **Measure** real timings against the live Firestore region before/after.

**Entangled seam to decide holistically (don't rip out piecemeal):** the local static-data
export (`update:*` scripts → `src/lib/{cats,feeding-spots}-static-data.json`) is **not read at
runtime** but `cats-static-data.json` is also written each build by `fetch-static-assets.js`
(`saveStaticDataJson`) and read by the one-off `migrate-cats-to-firestore.js`. §7a should
decide its fate (revive / replace / remove). The removed Cloud Storage "push" path is
recoverable on branch `archive/static-data-cloud-export` — only relevant if §7a chooses an
admin-button re-export over build/server baking (it shouldn't).
